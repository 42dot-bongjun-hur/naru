# Architecture

## 책임 경계

Naru는 사이트 콘텐츠를 소유하지 않는 재사용 가능한 엔진으로 설계합니다.

```text
site project A ─┐
                ├── shared Naru package ──> each site's own output directory
site project B ─┘
```

각 사이트 프로젝트가 소유할 항목:

- 사이트 이름, 원본 URL, 기본 경로, 분류명 등 사이트 설정
- Markdown 글과 정형 데이터
- 템플릿, 스타일, 이미지와 기타 정적 파일
- 빌드 결과물 및 배포 설정

Naru가 소유할 항목:

- 설정 파싱과 검증
- 콘텐츠 로딩 및 front matter 정규화
- URL/출력 경로 계산
- HTML 렌더링과 정적 리소스 복사
- RSS, sitemap, robots.txt 등 선택적 산출물 생성

사이트 간 공유는 엔진 패키지 또는 Git submodule로 연결하되, 생성 결과는
공유하지 않습니다. 따라서 한 사이트의 빌드가 다른 사이트의 콘텐츠나
배포 디렉터리를 덮어쓰지 않아야 합니다.

## 패키지 경계

- `cli`: 명령행 인자와 사용자에게 보여줄 오류 처리
- `config`: 사이트 설정 로딩 및 검증
- `content`: 파일 탐색, front matter 파싱, 콘텐츠 정규화
- `render`: 템플릿을 이용한 페이지 생성
- `output`: 경로 안전성, 파일 쓰기와 정적 리소스 복사
- `seo`: RSS, sitemap, robots.txt 및 검색 엔진 메타데이터

이식된 엔진은 아직 모듈 전역 설정을 사용합니다. CLI는 빌드마다 별도 Python
프로세스를 실행해 사이트 설정이 섞이지 않도록 합니다. 향후 공통 엔진으로
정리할 때 명시적인 빌드 컨텍스트로 교체할 예정입니다.

## 현재 마이그레이션 상태

첫 단계에서는 `astro-paper/builder`와 루트 `build.py`의 생성 로직을
`src/naru/engine`으로 옮겼습니다. `naru build`는 사이트 루트와 출력 디렉터리를
받으며, 출력 경로를 분리해 기존 배포 파일을 건드리지 않고 검증할 수 있습니다.

사이트별 상수는 사이트 루트의 `naru.yml`에서 로드하고 검증합니다. 다만
devbj.com 전용 렌더링 및 템플릿 가정은 엔진에 남아 있습니다. `ts.devbj.com`
호환성은 아직 구현하거나 검증하지 않았습니다.

## 초기 설정 스케치

`examples/basic-site/naru.yml`은 현재 설정 필드의 예시입니다. 예제 사이트에는
빌드에 필요한 devbj.com 호환 템플릿과 정적 파일이 포함되어 있지 않습니다.
기존 두 사이트의 URL 규칙과 콘텐츠 형식의 차이는 별도 호환성 검증이 필요합니다.

## 호환성 원칙

- 기본값은 명시하고, 잘못된 설정이나 누락된 파일은 원인을 포함해 실패시킵니다.
- 사이트별 URL 경로와 출력 루트를 빌드마다 명시적으로 지정합니다.
- 생성 파일과 사용자가 관리하는 정적 파일의 소유권을 구분합니다.
- 기존 사이트로 전환할 때 생성 결과를 비교할 수 있도록 단계별로 기능을 옮깁니다.
